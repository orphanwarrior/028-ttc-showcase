# 记录一下开发中遇到的几个问题

整理项目时，筛选几个我觉得值得单独讲的设计问题。

这些问题在当前代码中都有对应实现。有些地方我也会提到其他做法，主要是为了说明当时为什么这么设计，并不代表所有方案都实际尝试过。

## 一、校核通过的是哪一版草稿

TTC的专利撰写流程中，草稿会经过多次生成、修改和校核。这里有个比较容易忽略的问题：如果第一版草稿通过了校核，之后又修改了正文，之前的校核结论还能不能用？

显然不能。但如果系统只是给任务记录一个【校核通过】的状态，就可能出现新草稿沿用旧报告的情况。

目前的处理方式是将校核报告与草稿修订号、SHA-256内容指纹绑定。后续使用报告时，必须先确认它对应的仍然是当前草稿。人工确认后，才会形成供下一阶段使用的正式版本。

这意味着每次修改都要处理校核状态，必要时还得重新检查，确实增加了一些复杂度。不过在专利撰写场景下，我认为至少要能回答这份校核报告，当时检查的究竟是哪一版内容。


## 二、生成开始时有效，不代表结束时还有效

TTC的一次模型调用可能持续几分钟。比如生成实施例时，系统读取的是用户已经确认的权利要求，但生成过程中，用户可能又修改了上游内容。

如果模型返回结果后直接写入当前版本，就可能把基于旧权要生成的说明书当成最新结果。

这里采用了两次检查：任务开始时记录输入版本，模型在数据库事务外完成生成；等到结果准备发布时，再检查上游确认版本和任务启动时记录的当前版本是否仍然匹配。

因此，即使模型已经成功返回，也不意味着结果一定能成为当前稿。遇到版本冲突，生成结果会保留记录，但不能直接发布。

附图部分还需要区分两种变化：如果改变了附图所表达的技术内容或部件关系，下游说明书需要相应失效；如果只是调整排版，在通过验证的情况下，不必重新生成说明书。

这部分处理起来比较繁琐，尤其是已经消耗了模型调用费用，却因为版本变化而无法发布的情况。但直接覆盖会带来更难排查的问题。


## 三、重新生成失败，原来的稿子还得在

这个问题比较耿直。用户已经有一份可以继续修改的附图或实施例，点击重新生成后，如果新任务立刻取代当前版本，一旦模型超时、报错或者校核失败，原来的工作稿也可能跟着丢失。

现在新生成的内容会先作为独立尝试保存，包括中间草稿、模型调用记录和校核结果。只有通过检查，并且发布条件仍然成立时，才会切换当前版本。

失败的任务不会覆盖旧稿，用户仍然可以继续处理原来的内容。

代价是数据库里会留下更多历史记录，前端也需要明确区分「当前工作稿」和「尚未成功的生成尝试」。

另外，TTC可以利用已保存的中间草稿继续处理，但这不等于模型能够从上次中断的位置无缝恢复。涉及模型重新调用的部分，仍然可能产生新的结果。


## 四、让模型自己修正，但不能无限重试

最开始考虑Agent执行流程时，有一个问题：模型生成的内容如果没通过检查，应该直接失败，还是允许它再修一次？

直接失败比较容易实现，但有些错误其实只需要补充证据或修改局部内容。反过来，如果一直允许模型自行尝试，又可能出现反复修改、消耗大量token，最后依然没有合格结果的情况。

目前TTC为各阶段设置了有限的操作范围，包括回查证据、更新草稿、运行检查和独立校核。

考虑到个人api成本和ds的高峰价格，附图与实施例相关任务的默认预算是最多6次模型调用，最多90,000个已报告tokens；最长240秒。

出现关键事实缺口、用户取消或预算耗尽时，执行流程就会停止，并保存已有状态。

但是，不是所有模型供应商都会完整返回token用量。因此，未报告的用量会单独记录，而不是直接算成0。预算控制也无法保证单次调用绝对不超额。

模型接口层没有设置整次请求的自动重跑。任务失败后，是否重新尝试由用户决定，避免一次操作在后台产生多轮不可预期的调用。
